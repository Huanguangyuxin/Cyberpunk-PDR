## 2. 原文结构与系统性理解

### 2.1 工具选择：按任务选择环境和几何生产方式

[原文 S1：Choosing Your Gemini Tools / Choosing your 3D Tools] 教程区分 AI Studio 快速浏览器场景、支持长任务和本地 Blender 管线的 agentic IDE，以及可自定义多 Agent 与工具调用的 Gemini API。多数程序化或风格化场景可以代码生成；高细节主体适合 Blender Python 建模，经 GLB 导出进入实时场景。原例通常使用 Three.js，不能把该选择视为所有 3D 任务的必要条件。

[项目适配] 保留“根据任务分配 DCC 与实时渲染职责”，运行时固定自研引擎；GLB 是待核实的中间格式而非无损承诺。是否支持材质扩展、灯、实例、透明和体积效果均须查现有接口并实测。

### 2.2 六个核心工作流

**W1：先对齐创意方向。** [原文 S1：1. Align on creative direction first] 输入照片、草图、短环绕视频或研究得到的参考；用 Nano Banana 制作场景和重点物件概念效果，先对齐光照、尺度和情绪。通过 `/grill-me` 或自然语言提问澄清相机、尺度、玩法与实现方式；确认后生成包含里程碑的 PLAN.md 和可衡量的 `/goal` 提示词，并可规划无缝纹理。示例要求概念得到用户认可后再编码。

理解：长时间自治前，先把“做得好看”转成可共同检查的视觉目标。对本项目，玩法问题被删除，替换为展示范围、机位、输出平台、质量与预算问题。教程命令不能默认存在于 Cursor，也不能直接当作 Codex 自动执行接口。

**W2：主 Agent 统筹并行专业子 Agent。** [原文 S1：2. Ask Argon to orchestrate parallel subagents] 将世界拆成相互独立的地形、建筑、植被、道具、光照和物理等任务；协调共享坐标与架构并合并结果，避免一个 Agent 在巨型文件里依次包办全部内容。

理解：并行依赖清楚的接口和责任边界。本项目采用空间、材质、灯光、资产、引擎集成分工；不照搬不需要的地形或玩法任务。文件锁、写入白名单和版本契约为项目扩展，原文未给出完整实现。

**W3：每轮调用独立对抗式批评 Agent。** [原文 S1：3. Tell Argon to invoke an adversarial critic subagent] 制作者易过早满意，需另一个批评者根据实际截图反馈。示例每轮要求四类视图：3/4 全景看构图、近景看纹理、低角度看落地、线框看几何与穿插；提出至少三个具体缺陷并十分制评分，以 9/10 为示例门槛。仅使用 AI Studio 时可上传截图请求批评。

理解：独立审查比制作者自报完成可靠；四类视图共同约束真实性。原文线框只是诊断手段，不能单独证明无碰撞或结构正确。项目不将主观 9 分当唯一验收，也不要求无缺陷时编造三个问题；需说明检查范围与未发现的证据。

**W4：给人类美术指导建立工具。** [原文 S1：4. Let Argon build the tools to keep you in the art director’s seat] 每个里程碑保存有标题和版本的截图到 `progress.html`；提供光照、粗糙度、相机等实时控制，导出 JSON，再将确认值写为默认配置。最终可移除临时控制。

理解：用户对氛围的选择不能全交给自动评分。项目的画廊必须标注引擎、版本、机位和渲染设置；调参回写已有唯一配置源，不能建立与引擎配置分叉的旁路。

**W5：用当前 3D 截图生成可对照的目标图。** [原文 S1：5. Use Nano Banana to Improve 3D Renders] 隐藏 UI，选择 3–5 个关键视角生成保持相机、构图和建筑布局的 2K 写实目标；比较实际截图与目标，持续修改真实几何、shader、材质和光照。明确不能把目标图贴成平面背景冒充 3D。

理解：同机位比较比泛泛要求“更写实”更可执行。图像模型可能改动尺度和结构，目标需先做一致性检查。目标图是方向证据；实际实时渲染才是效果证据。Nano Banana 在当前环境和 Cursor 中是否可调用未验证，不能将其他模型输出冒称该模型。

**W6：复杂空间先用 2D 空间指南固定比例。** [原文 S1：6. For your most complex builds, ground proportions with a 2D plan first] 多房间/复杂建筑先画带米制尺寸的俯视平面（例如 SVG），确认房间、柱和路线，再依据坐标构建 3D。参考照片可叠编号 XY 网格辅助比例分析；精确复现照片时先估计相机角度、地平线。

理解：照片网格并不能单独求出真实尺寸，仍需尺度锚点和透视估计。本项目将这项原文的可选建议提升为强制全场设计闸门，并增加剖面、标高、灯光与材质设计；这些完整交付要求来自用户而非原文。

### 2.3 Desk Racer 案例及限度

[原文 S1：Putting it all together] 作者用桌面照片、概念图和访谈形成计划，再以长目标及子代理协作 Blender 与实时场景；文中报告了支柱相交数学检查、每轮自动截图，并描述通过调整世界比例和相机保持车辆屏幕大小、改变空间感的迭代。

可复用的是“方向对齐→分工执行→几何检查→截图检查→调整”的工作流。它是游戏案例，不是本项目性能、高保真或自动化成功率的证明；其玩法、Three.js、首个可玩版本的扩展节奏不直接适用本项目，也不构成 Vertical Slice 依据。

## 3. 直接复用、改造与新增的边界

可直接复用：参考驱动、先澄清后制作、概念评审、共享坐标的任务拆分、Blender Python 制作细节、多视角检查、独立批评、实际 3D 迭代、阶段截图画廊和参数固化。

需要改造：Three.js 加载与调参改为自研引擎现有资产和配置系统；截图从通用浏览器改为实际运行的引擎视口；纹理和材质经过引擎颜色空间/通道/透明支持检查；灯具不能假设 GLB 自动带入；长任务命令改为实测可用的 Cursor 调度途径；主观评分结合硬性质量闸门。

项目新增：完整概念/平面/剖面/照明/材质/资产设计作为生产前置；资产 ID 和版本依赖；能力验证矩阵；可重复生成、哈希、失败隔离、回滚；基准相机与固定输出；性能预算；问题分级与修复复验；长期文档和决策审计。S1 没有给出这些工程规则的完整规范。

## 4. 工具调用和资产集成契约 [项目扩展]

### 4.1 能力发现先于使用

首次接入记录：工具/应用名称、版本、可见模型实际名称、权限、连接方式、可用操作、最小只读结果和日志路径。前置任务结束时仅验证原教程与本地资料可读写；正式执行轮次的真实更新见TOOLCHAIN_STATUS.md与PROGRESS.md，不把前置状态当作永久能力结论。存在 Blender 工具不等于连接可用。

引擎需逐项建立能力证据：基础光照/PBR、阴影、局部反射、玻璃与水、体积、后处理、截图/调试视图、导入格式与目标平台。区分“文档描述”“接口存在”“最小探针成功”“全场已验证”。功能缺失登记缺口，先提出兼容实现或有依据的变更，不偷换运行时。

### 4.2 可重复执行记录

每个实际工具操作记录 `run_id / task_id / 输入版本及哈希 / 工具版本 / 参数及随机种子 / 前置条件 / 写入白名单 / 实际调用或脚本路径 / 起止时间与退出结果 / 输出哈希 / 后置检查 / 证据路径`。失败日志也保留，敏感凭据不写入。模板字段未填写属于未执行。

Python/DCC 脚本以参数驱动；对象使用稳定 ID/集合，不按随机对象名追加；重复执行应替换受管结果或产生隔离新版本，不翻倍生成。导出前检查单位、包围盒、法线、UV、厚度、依赖纹理和材质槽；变换仅在明确边界应用一次。不要跨 Agent 同时操控同一 live Blender。

资产契约包括源文件、生成脚本、导出文件、资产 ID、版本/哈希、来源与使用权限、米制尺寸、坐标/朝向/枢轴、拓扑/三角形和纹理预算、UV 与 texel density、材质槽、贴图色彩空间/通道、LOD（如需）、依赖、引擎映射与已知降级。预算数值在平台/性能目标明确后冻结，当前没有实测阈值。

历史约定候选：Blender Z-up，X 右、Y 由入口至后墙；引擎 Y-up，转换 `(x,y,z) → (x,z,-y)`。须用非对称标记物验证位置、朝向、法线、切线和相机，确认导入器是否已转换，防止二次转换。

### 4.3 材质、灯光与渲染适配

确认 sRGB 颜色纹理与线性数据纹理、法线方向、粗糙度/金属度/AO 打包与映射。Blender 节点效果不保证导出；必要时烘焙并验证。确定引擎的曝光、色调映射、光强单位与发光/照明关系。环境贴图反射不等于室内局部物体反射；按真实支持选择并验证反射方案。玻璃/液体须验证排序、厚度/折射支持；体积灯束须验证遮挡，不能用全屏雾掩盖缺陷。

### 4.4 回滚与失败处理

修改前保存受影响源文件、参数和上个已验证包的快照/哈希；Git 如可用只提交本轮明确文件，不把既有巨大资产批量提交。大型 .blend、纹理和导出件须另有版本化存储，Git 提交号不证明这些文件已经备份。

候选输出写入隔离版本目录，验证通过才更新活动引用；禁止覆盖唯一源文件。失败保持上个已验证状态，记录失败步骤和待解决项；重试须说明改变的条件，不能无限重复失败调用。回滚恢复代码、资产、灯光/材质参数、清单与引用这一整套版本，并在同机位复验。没有实际恢复演练时标注“回滚方案未演练”。

## 5. 视觉审查闭环 [原文机制＋项目扩展]

固定设计基线与相机→制作候选→自研引擎加载→采集 Beauty 和诊断证据→独立批评→问题登记→按问题修复→同条件复拍→独立复验→合并或回滚。

每轮覆盖入口全景、舞台/舞池、吧台、卡座、二层/楼梯、水带、后场以及至少一个低角度接触和材质近景；四类基础视图不能省略。Engine 无线框时提供可用的几何/深度诊断及 Blender 线框补充，并明确它们不能替代引擎 Beauty；缺少关键证据仍为待验证。

截图清单字段：`review_id / 场景与引擎版本 / 资产清单哈希 / camera_id 与位置朝向/FOV / 分辨率 / 时间或随机种子 / 曝光/色调映射 / 渲染质量和效果开关 / 图片路径与哈希 / 实际采集方式`。固定比较条件；若调整曝光或视角，保留旧条件回归图。阶段画廊只引用真实图片。

问题格式：`issue_id / review_id / camera_id / 缺陷和可见证据 / 严重级别 / 对应设计要求 / 建议根因（假设须标注）/ 责任人 / 修复版本 / 复验图片 / 状态`。严重级别：阻断（错引擎、假 3D、空间矛盾、关键功能缺失、证据失真）；主要（穿插、悬浮、阴影漏光、材质错误、焦点失控）；次要（局部重复、轻微细节）。

可按构图、空间、几何、材质、光照/阴影、反射/体积、后处理与一致性记录十分制评分，9 分作为项目拟用参考；终验还必须阻断/主要问题清零、全区域覆盖、真实引擎证据齐全、性能目标已定义并实测。次要遗留需明确列出并由用户接受。每轮最多三次同类修复仍无改善则升级根因调查，保留可用版本，不以换评分者宣布成功。

## 6. 生效范围和局限

这是可执行的规范，不是已完成的自动化平台。文件不会自动创建 Cursor 会话、启动 Gemini、截图或形成定时循环。跨会话遵守靠入口文档和派工回执，技术上的强制执行还需后续验证。下一阶段按生产计划先完成全场设计；仅当发现缺失且影响设计的技术信息时做获授权的最小能力调查，不先批量生产。

## 2026-10-28 正式执行经验补充 [项目扩展]

实际将平面/投影导图与风格板送入image_gen后，六幅概念仍出现视锥外卡座、折返梯变直梯、阵列数量变化。说明“给了参考/尺寸”不足以保证生成图空间一致；必须对同一空间JSON做独立投影和逐物件核对，不能因画质好看而通过。风格板v1被用户拒绝，v2独立审查指出噪点与近似图案，v3改用原创SVG源并限定只作视觉语言，不能提取其建筑布局。

Cursor桌面Gemini曾在大任务中Provider Error，仅写了备份；同模型小任务重试和执行总控可重复脚本成功。需区分脚本作者、实际执行者和审查者；错误、未完成字段及独立检查unverified状态都保留，不把Completed UI或零fail等同完整验收。

## D-015 源驱动设计与双重闸门 [用户要求＋项目扩展]

本轮先建立可消费的源数据（材质节点参数、原创矢量/图层、物件变换、灯具结构与活动灯组），再由冻结空间生成真实Blender设计模型、相机矩阵、灰盒/对象ID/线框/真实深度。ID与深度属于几何诊断，不把2D数学投影叫真实渲染。楼梯末级与平台连接、家具占用包围、视场与真实遮挡分别核查；frustum包含不保证没有遮挡，可见机位字段只作设计意图。

生成图若不能保持实体轮廓与投影，不以文字提示无限修补。采用真实DCC灰盒/设计着色作为几何权威，受约束编辑仍需对照ID/深度复审；漂移版本保留且不晋级。允许设计模型不等于允许正式资产批量生产。Cycles间接光/阴影/透射只证明DCC设计样板，不证明自研引擎同类功能。

G-D1空间与G-D2风格分别由独立审查者出结果；制作者不能换身份自验。7项数字通过不构成G-D1整体验收，更不能代替G-D2。两者和用户批准共同控制生产；150个旧设计/参考文件在本轮建立保留哈希，修改须追踪，不删除失败证据。该流程是针对本项目已发生缺陷增加的工程实践，不冒称原教程逐条提出。
